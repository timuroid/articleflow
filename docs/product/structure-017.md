# Структурное приведение статьи к шаблону

## Зачем это нужно

Исходная статья может быть написана не в порядке, который требует эталон: постановка проблемы находится в основной части, цель пропущена в аннотации, сверху добавлена рабочая редакционная строка. Одной замены шрифтов недостаточно. Редактору нужен DOCX с расположенными по шаблону **существующими** фрагментами и понятным перечнем недостающих данных.

Этот документ фиксирует решение пользователя, принятое после пилота с эталоном «Русского инженера». Публичный GitHub `main` на 17 октября 2026 года содержит исследовательский CLI 0.7; в отдельной локальной ветке восстанавливается ограниченный Web 017. [Техническая карта утраченного релиза](../tech/web-017-recovery.md), [новая реализация](../tech/web-017-local.md), [развёртывание](../tech/deployment-caddy-017.md).

## Путь редактора

1. Редактор загружает 1–10 правильно оформленных эталонов DOCX. При нескольких файлах он подтверждает, что они относятся к одному шаблону. Система показывает найденные различия и автоматически объясняет допустимые контекстные варианты, если имеет для этого доказательства.
2. Неоднозначные варианты оформления и структуры показываются с точным источником. Редактор выбирает верное правило только там, где система не может обоснованно решить сама. Утверждённая версия шаблона неизменяема.
3. Редактор загружает одну или много новых статей. Для каждой система составляет карту абзацев, таблиц и объектов, назначает роли и сравнивает их со слотами шаблона.
4. Подтверждённые фрагменты переставляются в нужный порядок. Если роль отсутствует, система вставляет явно помеченное место для заполнения и объясняет, какие сведения нужны. Она не придумывает научный текст, авторов или результаты.
5. Редактор может указать роль фрагмента, подтвердить разделение абзаца на части, внести недостающие сведения или вынести рабочую заметку отдельно. После каждого решения формируется новая ревизия результата, исходник остаётся доступным.
6. Готовый DOCX выдается только после структурных и технических проверок. Иначе скачивается черновик с замечаниями. В пакетном режиме ошибки одной статьи не останавливают другие; ZIP содержит manifest статусов.

### Слоты конкретного русского научного образца

УДК → заголовок → авторы → организация → город → email → заголовок аннотации → **постановка проблемы** → **цель** → **результаты** → **практическая значимость** → ключевые слова → основная часть. Служебную рабочую строку нельзя принимать за авторов; она может быть вынесена в отдельные редакционные заметки. Заголовок «Проблема и постановка» в основной части не равен постановке проблемы *внутри аннотации*. У другого утверждённого шаблона слоты и обязательность могут отличаться; наблюдаемый образец не является универсальными правилами редакции.

## Дополнительные требования

| ID | Проверяемое поведение |
| --- | --- |
| PRD-023 | Шаблон хранит порядок и обязательность смысловых слотов отдельно от оформления. Одноимённые роли разных областей документа не смешиваются. |
| PRD-024 | Система может переносить подтверждённые исходные фрагменты, не переписывая их научное содержание. План фиксирует источник каждого фрагмента; разрезание сложного OOXML без доказательства сохранности запрещено. |
| PRD-025 | Недостающие обязательные слоты и неразобранные части аннотации получают видимые заполнители/вопросы. Пользователь вводит сведения сам; такой результат не помечается готовым до проверки. |
| PRD-026 | Несколько эталонов сравниваются по наблюдениям и происхождению. Противоречия становятся явными вопросами; утверждение создаёт новую неизменяемую версию. Пакетная обработка сохраняет отдельный статус и отчёт для каждого DOCX. |

Проверять также формальные и визуальные свойства: реальный шрифт Arial/Times New Roman, размер, интервалы, выделение отдельных слов, подписи рисунков, формулы, изображения, таблицы и связи. Успех структуры не означает пиксельного совпадения страниц во всех версиях Word.

## Что не обещается этим срезом

Локальный Web 017 в прежней рабочей среде был однопользовательским. Полностью автоматическое корректное понимание произвольных документов, 100% точность на независимых статьях, удаление данных по retention и многопользовательская изоляция не доказаны. Рабочие документы и эталоны не публикуются в репозитории. В новой локальной ветке основные HTTP-пути проверяются интеграционными тестами; [SC-080–SC-085](scenarios/structure-web.feature) пока не имеют восстановленных step definitions и не объявляются исполненными BDD-сценариями.

## Уточнение 021: наблюдаемые интервалы и полнота

Отдельная подпись ключевых слов, автоматическая нумерация и пустая строка
перед заголовком являются частью шаблона. Их наличие проверяется отдельно
от правильности шрифта текста. Один заголовок без ключевых слов не закрывает
обязательный блок. Наблюдённые, но отсутствующие необязательные сведения
показываются в отчёте для проверки обязательности.

Для извлечённых межблочных интервалов утверждение требует успешного
контрольного рендера; несовпадение блокирует версию. Реализованный охват
проверки и пределы — [контракт 021](../tech/transfer-021.md).
