# Применение шаблона к исходному DOCX, профиль I3

PRD-005, PRD-006, PRD-013, PRD-015. Отдельный production baseline: источник сохраняет собственное оформление. Результат этого профиля не засчитывается как реконструкция очищенного I1/I2-входа и не меняет прежний эталон.

Модель назначает только роли блоков. План ролей связан с SHA-256 входного DOCX и обязан покрывать каждый блок ровно один раз. Runtime извлекает структуру, исходные свойства и spans **из обрабатываемой статьи**. Исходный образец шаблона, его oracle-план и golden PDF не читаются.

Выбор свойств:

1. Для paragraph/layout/drawing применить однозначное структурное правило, если оно есть.
2. При отсутствии правила сохранить исходный вариант, если он входит в допустимые варианты этой роли/элемента шаблона.
3. Для неизвестного варианта разрешить только однозначное сопоставление после исключения управляемой типографики: семейство обычного шрифта, кегль; для абзаца также spacing/ind/jc. Прочие свойства должны совпадать. Несколько совпадений означают `needs_review`, а не выбор по частоте или расстоянию.
4. Неизвестные геометрия/секции без правила требуют проверки. Текст, spans и порядок берутся из входной статьи.

Это не универсальный импорт произвольного Word-файла: текущая реализация требует совпадения bundles styles/theme/numbering/settings. Несовместимые ресурсы блокируются, чтобы одинаковые style IDs из разных файлов не интерпретировались молча по-разному. Поддержка миграции ресурсов — отдельная работа.

Сборщик создаёт новый body и DOCX из нейтрального содержимого и выбранных свойств. Отчёт отдельно считает сохранённые, сопоставленные и выбранные правилом варианты. Наблюдаемые правила сохраняют статус research draft. Сохранение допустимого исходного варианта не означает, что удалось вывести авторское оформление из текста. При несовместимости результат DOCX не выдаётся; причины сохраняются в отчёте.

Проверки: точная повторная сборка уже соответствующего образца; изменение синтетического текста; исправление шрифта, кегля и интервала; отказ при неоднозначном сопоставлении, неизвестной роли, неверном source hash и несовместимых ресурсах. Реальные unseen статьи оцениваются отдельно.

## Команды и модельная серия

`format-source TEMPLATE_DIR SOURCE.docx ROLE_PLAN.json OUTPUT_DIR --rules RULES.json` принимает роли в `source-roles-0.7`. Они содержат `source_sha256` и массив `blocks` с полями `id/role`. Итог сохраняется как `OUTPUT_DIR/candidate.docx`, если нет нерешённых вариантов и научное содержание прошло проверки.

`source-trials --help` описывает runner свежих вызовов. Он использует общий ledger и фиксирует prompt/schema/source/template/rules hashes, модель, reasoning и тарифы. Один POST на попытку, без repair. Прежде чем отправить запрос, нейтральное содержимое заново сверяется с исходным DOCX. Модель видит только роли, текст, наличие объектов и принадлежность таблице; исходные visual properties доступны compiler в I3. Target oracle и golden читаются только evaluator после ответа.

В отчёте `observed_full_match` относится к I3. `strict_I1_pass` остаётся false даже при нулевой разнице пикселей.
