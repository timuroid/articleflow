# Архитектура

## Контекст и решение

Предлагается модульный монолит с отдельными worker-процессами для тяжёлой обработки. Для небольшой редакции это уменьшает число развёртываемых сервисов, сохраняя возможность масштабировать обработку DOCX отдельно от API. Первое решение проверяется исследовательским прототипом; окончательные версии библиотек фиксируются при появлении кода.

| Компонент | Предложение | Ответственность |
| --- | --- | --- |
| Web | React + TypeScript + Vite | Загрузка, правила шаблона, вопросы, история и результаты |
| API | Python + FastAPI + Pydantic | Авторизация, контракты, версии, команды заданий, выдача артефактов |
| Worker | Python + Celery | Парсинг, LLM-классификация, план, OOXML-преобразования, проверки |
| База | PostgreSQL + SQLAlchemy/Alembic | Метаданные, состояния, решения, аудит и outbox |
| Очередь | Redis как брокер Celery | Доставка сигналов о работе; не источник истины о заданиях |
| Объекты | S3-compatible storage | Исходники, снимки пакетов, итоговые DOCX и отчёты |
| DOCX-слой | zipfile + безопасный lxml; python-docx вспомогательно | Сохранение пакета и точечные изменения OOXML |
| LLM gateway | Адаптер OpenAI-compatible API | Структурированные запросы к выбранному провайдеру, лимиты и журнал usage |

Браузер обращается только к API и ограниченным ссылкам загрузки/скачивания. API сохраняет команду в PostgreSQL; outbox-публикатор отправляет job ID в брокер. Worker берёт версионированные входы, читает объектное хранилище, выполняет этапы, фиксирует результат. Модель вызывается только из серверной среды.

## Границы модулей

`identity` проверяет сессию и membership; `documents` принимает и инвентаризирует пакеты; `templates` хранит наблюдения и версии; `jobs` управляет состояниями и review; `document_engine` выполняет чистые преобразования; `llm_gateway` инкапсулирует провайдера; `validation` строит доказательства сохранности; `artifacts` управляет скачиванием и retention.

Движок документов не зависит от HTTP и UI. Он получает immutable package snapshot, утверждённые правила, mapping блоков и параметры, а возвращает новый пакет, mapping и протокол проверок. Доступ к сети движку не нужен. LLM не получает файловую систему и не управляет исполнителем.

## Почему не генерировать DOCX целиком моделью

Генерация нового текста или XML моделью несёт риск потери payload. Рекомендуемый G-PLAN разделяет интерпретацию и сборку: student выдаёт роли, inline spans и object bindings, compiler превращает их в операции, renderer собирает DOCX. G-FULL сравнивается как исследовательский вариант. Сильный extractor и малый planner имеют разные профили; уточнение — [ADR-003](adr/003-template-research.md), исходное основание — [ADR-001](adr/001-document-engine.md).

## Нефункциональные свойства

- API не держит HTTP-запрос открытым на всё время обработки; создание задания возвращает `202`.
- Одно задание изолировано по памяти, времени, временной папке и workspace ID.
- Доставка очереди как минимум один раз; бизнес-переходы и публикация артефактов идемпотентны.
- Повтор исполнения сохранённого плана не вызывает модель и воспроизводит семантический результат. Побайтовое равенство ZIP не обязательно из-за timestamps и метаданных.
- Если безопасное преобразование не доказано, результат не публикуется как готовый.
- Отказ модели не должен повреждать исходник или делать API недоступным.

## Альтернативы и расширение

Микросервисы отложены до подтверждённой нагрузки. `patch_source` сохраняет OOXML новой статьи; `rebuild_neutral` нужен для честной реконструкции и имеет отдельные ограничения. Round-trip через LibreOffice не подменяет сохранение исходника; визуальный renderer фиксируется явно. Пакетная обработка входит в целевой MVP: Batch группирует jobs и ZIP exports по [контракту](batch-processing.md).
