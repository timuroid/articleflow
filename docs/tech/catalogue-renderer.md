# Каталог вариантов и сборщик 0.4

Этот срез исправляет недостаточность представления оформления в прототипе 0.3. На предоставленном образце достигнуто точное контрольное восстановление: [измерения](../research/renderer-004.md). Модель не вызывалась; правильный план получен из исходника и хранится отдельно. Требования: PRD-005, PRD-007, PRD-013, PRD-015.

## Почему одного стиля на роль недостаточно

Смысловая роль отвечает на вопрос, что это за текст. Свойства оформления отвечают на вопрос, как он выглядит. Несколько абзацев с ролью `body_ru` в образце имеют разные интервалы, отступы и свойства знака абзаца. Внутри абзаца меняются не только bold/italic/vertical, но также шрифт, кегль, язык, цвет, кернинг, лигатуры и явные сбросы свойств. При выборе наиболее частых свойств часть информации необратимо терялась.

Версия 0.4 хранит все наблюдённые варианты без привязки к номерам абзацев. У роли есть множество допустимых paragraph style IDs и character style IDs. Равные наборы свойств переиспользуют один ID. Выбор конкретного варианта относится к DocumentPlan. Условия автоматического выбора ещё нужно подтвердить: наличие варианта не превращает случайную ручную правку автора в правило журнала.

## Разделение файлов

```text
package/
  template/
    rules.json          # роли и каталоги свойств; без текста/IDs блоков статьи
    resources.zip       # styles, numbering, settings, themes, fonts
  content/
    content.json        # текст, порядок абзацев, структура ячеек, ссылки и markers
    payload.zip         # media, relationships, метаданные и прочие разрешённые части
    objects/*.xml       # непрозрачные научные формулы OMML
  oracle-plan.json      # контрольные назначения; не часть runtime-шаблона
  manifest.json         # метод, количества, ограничения
```

Ни в `resources.zip`, ни в `payload.zip` нет `word/document.xml`. Сборщик создаёт эту часть с нуля. В content нет paragraph/run properties, геометрии рисунков, ширин таблиц и секций. Рисунки в content содержат идентификаторы ссылок и описательные метаданные; геометрия вынесена в каталог. Формулы сохраняют внутренний XML, включая собственное оформление, поэтому протокол не называется чистым текстом или строгим I1.

План не спрятан в runtime-пакете: `render-catalogue` принимает его отдельным обязательным аргументом. Исходный DOCX, evidence и файл oracle на этапе сборки не читаются. Проверка этого свойства включает удаление исходника перед сборкой синтетического документа.

## Каталоги свойств

| Группа | Что сохраняется |
| --- | --- |
| paragraph | Полный `pPr`, включая интервалы, отступы, numbering, borders и `rPr` знака абзаца |
| character | Полный `rPr`, включая наследуемые style references и явные значения свойств |
| table | `tblPr` и `tblGrid` |
| row | `trPr` |
| cell | `tcPr`, включая ширины и объединения |
| section | `sectPr` |
| drawing | Blueprint `w:drawing`: размеры, crop, положение; вместо rIds/имён/описаний — placeholders |

Свойства компилируются из XML без преобразования единиц в округлённые числа. Убираются revision IDs и лишние namespace declarations. Пустой набор свойств — отдельный валидный стиль: отсутствие override нельзя автоматически заменять наиболее частым override.

ID имеет вид `character-<hash16>` и зависит от сериализованного набора свойств, не от block ID или текста. Проверяется коллизия. Это локальный стабильный идентификатор компилятора, не обещание семантического равенства произвольных XML с другим порядком свойств. ZIP ресурсов пишется с фиксированными timestamps и порядком элементов; повторное извлечение одинакового входа даёт одинаковые hashes пакета.

Word inheritance не разворачивается в воображаемые effective values для всех свойств. Полные ссылки и ресурсы стилей сохраняются, а каскад применяет движок документа. Это снимает часть ошибок ручного вычисления наследования, но связывает результат с зафиксированными ресурсами и renderer profile.

## План 0.4

```json
{
  "schema_version": "catalogue-0.4",
  "provenance": "source_oracle",
  "template_sha256": "hash of rules.json",
  "input_sha256": "hash of content.json",
  "blocks": [{
    "id": "b-000001",
    "role": "body",
    "paragraph_style": "paragraph-<hash16>",
    "spans": [{"start": 0, "end": 8, "style": "character-<hash16>"}]
  }],
  "layout": [],
  "objects": [],
  "section_style": "section-<hash16>"
}
```

Пример показывает форму; hashes и IDs намеренно условные. Спаны покрывают весь обычный текст без пропусков и перекрытий. Это низкоуровневый compiled plan, не утверждённый компактный ответ LLM. В будущем высокоуровневые semantic spans могут компилироваться в такой план; текущий model runner 0.3 на новую схему автоматически не переведён.

`layout` назначает style ID существующим table/row/cell nodes. `objects` назначает drawing style и стиль содержащего его run существующему occurrence. Текст, числа, формулы и картинки в план не перегенерируются. В таблице структуры остаётся только порядок узлов; геометрия задаётся выбранными стилями явно.

Назначения source oracle строятся во время извлечения исключительно для проверки compiler/renderer. Передача их модели была бы утечкой ответа. Все контрольные метрики имеют `model_calls=0`, `plan_provenance=source_oracle`, `strict_I1_pass=false`.

## Алгоритм сборки

1. Проверить версии, hashes правил/содержимого/ресурсов, покрытие блоков и объектов, существование стилей и соответствие роли.
2. Убедиться, что текст atoms равен неизменяемому block text. Каждый occurrence объекта используется ровно один раз; повтор одного binary asset допустим через разные occurrences.
3. Создать новый `w:document/w:body`, восстановить порядок абзацев, таблиц, строк и ячеек из нейтральной структуры.
4. Вставить выбранные свойства абзаца. Разделить исходный текст по полным character spans, создать новые runs, вернуть ссылки и bookmarks на исходные текстовые позиции.
5. Собрать рисунок из layout blueprint, вернуть rIds и метаданные occurrence; вставить исходный OMML по hash.
6. Применить явно выбранные свойства таблиц и секции, собрать OPC из содержимого и ресурсов, записать новый DOCX.
7. Отдельно проверить содержимое, inline-флаги и позиции объектов/ссылок/bookmarks. Получить свежий PDF и сравнить все пиксели с golden.

Исходные run boundaries не хранятся как обязательная структура. Соседние участки с одинаковым стилем объединяются: в образце 1085 исходных runs превратились в 391 текстовый span. Одиннадцать `lastRenderedPageBreak` удалены как кэш старой пагинации. Новая сборка всё равно совпала по пикселям, то есть этот кэш ей не нужен.

PDF всегда создаётся в новой временной папке. Если LibreOffice не создал свежий файл, старый PDF не может стать ложным успешным результатом. Для измерения используются RGB-растры без alpha, одинаковые DPI, размеры и число страниц; допуска на пиксели нет.

## Проверки и ограничения

К проверкам 0.3 добавлен `placement_fingerprint`: позиции картинок, формул, границ гиперссылок и bookmarks относительно абзаца/символа. Это обнаруживает, например, обмен rIds картинок при неизменных текстах и файлах media. Количество runs или XML-узлов не используется как критерий сохранности.

Текущий профиль: одна секция, обычный текст, гиперссылки, bookmarks, таблицы, inline drawings и OMML. Пустые runs, колонтитулы и текст в notes/comments отклоняются, чтобы не проносить необработанный внешний вид в payload. Другие ограничения загрузчика 0.3 сохраняются. Это не полный Word engine и не готовый sandbox для произвольных файлов.

Объединения ячеек пока выбираются layout-планом и затем проверяются как часть содержимого; менять их произвольно нельзя. Смысловая связь caption ↔ figure group ещё не выведена: сохранена исходная позиция и структура, что достаточно для этого контрольного образца, но не заменяет будущий граф связей.

Пакет содержит наблюдённые альтернативы, а не полностью утверждённые условия применения. Переносимость проверена лишь синтетической заменой текста при том же наборе типов оформления. Для реального transfer нужны независимая статья, её целевой документ, модельный/семантический выбор вариантов и отдельные измерения. Подмножества embedded fonts могут не покрывать новые символы; этого не проверяет воспроизведение одного образца.

## Запуск без API

```bash
articleflow extract-catalogue \
  private-fixtures/pilot-001/source.docx \
  private-fixtures/pilot-001/annotations.json \
  private-fixtures/pilot-001/definitions.json \
  artifacts/catalogue-004

articleflow render-catalogue \
  artifacts/catalogue-004/template \
  artifacts/catalogue-004/content \
  artifacts/catalogue-004/oracle-plan.json \
  artifacts/catalogue-004-rebuilt.docx

articleflow pdf artifacts/catalogue-004-rebuilt.docx artifacts/catalogue-004-pdf
articleflow compare private-fixtures/pilot-001/source.docx artifacts/catalogue-004-rebuilt.docx \
  --golden-pdf artifacts/pilot-001/golden/source.pdf \
  --candidate-pdf artifacts/catalogue-004-pdf/catalogue-004-rebuilt.pdf
```

Папка извлечения должна быть пустой: старые результаты не перезаписываются. Версии `pilot-0.3` и `catalogue-0.4` несовместимы, старые планы не выдаются за новые. Миграция требует повторного извлечения из приватного DOCX и новой разметки вариантов. Старые model trials и отчёты сохраняются без изменения результатов.
