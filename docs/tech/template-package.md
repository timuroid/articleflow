# TemplatePackage: как хранить шаблон

## Рекомендация

Хранить шаблон как версионированный пакет декларативных правил и воспроизводимых ресурсов. Canonical источник — валидируемый JSON, а не свободный prompt и не исходная статья с заменяемыми словами. DOCX-образец остаётся evidence; он не является runtime шаблоном статьи.

Пакет хранится в object storage под immutable version ID; PostgreSQL содержит status, owner, version, manifest hash и ссылки. Из JSON компилятор создаёт короткие инструкции student и нужные OOXML styles. Сильная модель может предлагать правила, а утверждённая версия компилируется без модели.

## Состав пакета

```text
template-version/
  manifest.json                 # схема, версия, hashes всех ресурсов
  rules.json                    # канонические правила и ограничения
  renderer-profile.json         # движок, единицы, fonts, field policy
  compiled/student.json         # компактное представление для application model
  compiled/styles.xml           # сгенерированные безопасные определения стилей
  compiled/numbering.xml        # только если правила используют numbering
  assets/                       # только подтверждённые общие assets, по умолчанию пусто
```

Это логическая структура будущего артефакта; указанная папка не создаётся в публичном Git с реальным образцом. Evidence и original sample лежат отдельно с более узким доступом. `manifest` указывает их IDs для редактора, но student не получает эти ссылки и доступ. Источник и compiler version входят в provenance; checksum manifest считается по каноническому manifest body без поля собственного hash, hashes ресурсов — по их байтам.

## Слои правил

| Слой | Что хранит | Пример |
| --- | --- | --- |
| Page/section | Размер, поля, колонки, переносы, keep rules | A4, поля, запрещённый разрыв подписи и рисунка |
| Paragraph styles | Семейство/кегль шрифта, интервалы, отступы, выравнивание | body, title, abstract, heading_1 |
| Character styles | Только свойства диапазона символов | term_definition → bold, foreign_term → italic |
| Semantic rules | Когда назначать роль или character style | Выделить термин в его определении, но не все упоминания слова |
| Structural rules | Роли, кратность, порядок, обязательность | У рисунка одна связанная подпись; порядок разделов сохранить |
| Literal/label rules | Разрешённые служебные слова и разделители | «Ключевые слова:», «Рисунок {n} — » |
| Object rules | Размеры, способ размещения, подпись, связи | inline image, max content width, aspect ratio preserve |
| Exceptions | Приоритеты, fallback, неподдерживаемые случаи | Неуверенное определение термина → review |

У правила есть ID, typed properties, origin, evidence refs, confirmation и версия. В compiled/student остаются только нужные роль, условие и разрешённый style ID; evidence текста образца не попадает в model context. Sample-specific числовые параметры оформления допустимы как наблюдение, но block index или offset конкретного термина образца — не общее правило.

## Внутри одного абзаца

Абзац хранит текст один раз. Разметка — spans с `start/end`, semantic role и style ID. В TemplatePackage нет span-ов будущей статьи; там правило их выбора и визуальное отображение роли. Конкретные spans возвращает малая модель в DocumentPlan.

Пример: текст `Энтропия — мера неопределённости.`; диапазон `[0, 8)` получает `term_definition`, а правило шаблона отображает его полужирным. В другом шаблоне та же роль может быть курсивной. Если из контекста нельзя доказать, что это именно определяемый термин, нужен явный fallback, а не правило «любое первое слово выделить».

Различать semantic intent и текущий внешний вид. Исходный bold может быть случайным direct formatting, названием или авторским акцентом. Сохранение явного авторского emphasis и вывод нового term_definition — разные действия, отмечаемые отдельно. Супер/подстрочные индексы, формулы и значимые символы относятся к payload; их нельзя сбрасывать для соответствия общему шрифту.

Приоритеты: защищённый scientific payload → подтверждённые семантические ограничения → конкретное character rule → paragraph defaults → document defaults. Две конфликтующие concrete rules одного приоритета дают ошибку компиляции/плана. Объединение совместимых свойств разрешено явно; перечёркивание или hidden не выдаются student как свободные косметические опции.

## Подписи, служебные слова и изображения

Подпись — составная сущность: роль caption, связь `asset_id`, позиция before/after, нумерация/поле, separator, научный текст подписи и возможные inline spans. «Рисунок» и тире могут быть literals шаблона; описание эксперимента в подписи — текст статьи. Источник номера и REF/SEQ сохраняются, пока отдельный проверенный numbering adapter не разрешает преобразование. Regex не заменяет проверку ссылок.

Label policy: `reuse_if_present`, `insert_if_missing`, `replace_confirmed_label`. Вставка только из утверждённой allowlist, в конкретный slot и ровно один раз. Замена существующего label требует его надёжного отделения от научного текста; иначе review. Удаление неизвестного префикса запрещено. Изменения фиксируются как generated template content и учитываются в validator отдельно от original scientific payload.

Изображение хранится отдельно по asset ID и hash. Шаблон описывает positioning, max width, preserve_aspect_ratio, crop policy и связь подписи. Малая модель выбирает binding и rule ID, не переписывает binary/base64. В исходнике может быть важно значение crop: I1 без crop metadata не сможет восстановить его в точности, что отражается в discarded inventory. Новый crop в базовом профиле запрещён.

## Утверждение и переносимость

Проверки: полная типизация и единицы; валидные style refs; отсутствие циклов/конфликтов; поддерживаемые объекты; allowlist literals; отсутствие текста/изображений образца в runtime; совместимость renderer profile; синтетические примеры условий. Изменение character style, literal или условного правила создаёт новую версию всего пакета, поэтому старый batch воспроизводим.

Схема должна расширяться на другие типы документов через vocabulary/roles/slots; не пришивать `abstract` как обязательное поле любого документа. При этом универсальная онтология и универсальный extractor сейчас не реализуются: первый профиль `scientific_article` проверяется отдельно.

Иллюстрация канонических правил — [template.example.json](contracts/template.example.json); полный runtime контракт расширится после прототипа. Выбор между JSON, prose и очищенным DOCX остаётся предметом [исследования](../research/methods.md).

## Реализованный исследовательский профиль 0.4

[Каталог и сборщик 0.4](catalogue-renderer.md) реализуют полный набор вариантов свойств и отдельный план их назначения. Это версия `catalogue-0.4` для oracle-контроля, совместимость с контрактом v0.2 выше автоматически не предполагается. Шаблон не содержит текста образца и назначений по block IDs; правильные назначения хранятся отдельно. Самостоятельный выбор вариантов моделью ещё не измерен. Миграция из `pilot-0.3` требует повторного извлечения свойств; старые результаты сохраняют прежнюю версию.
