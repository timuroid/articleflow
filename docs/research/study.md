# Исследование представления шаблона и минимальной модели

## Цель и единица результата

Найти представление шаблона и способ применения, позволяющие небольшой модели за один вызов получать корректный план научного DOCX. Отдельно измерить точность, стоимость и время подготовки шаблона сильной моделью. Сначала проверить применение вручную подготовленного качественного шаблона; универсальный считыватель не является блокирующей зависимостью.

Результат исследования — воспроизводимый набор: версия TemplatePackage, метод извлечения, протокол входа статьи, application method, model/provider snapshot, renderer version, параметры inference, corpus split, таблица измерений и ограничения. Название модели без этого набора не является результатом.

## Вопросы и гипотезы

| ID | Проверяемый вопрос | Эксперимент |
| --- | --- | --- |
| RQ-01 | Достаточен ли переносимый шаблон для точного восстановления образца? | Ручной проверенный шаблон, свежий нейтральный документ, baseline renderer, 10 прогонов |
| RQ-02 | Как описывать выделения внутри абзацев? | Сравнить plain text, asset sidecar и сохранённые semantic spans; оценить exact span match |
| RQ-03 | Лучше ли ссылки на текст, чем повторная генерация всего текста? | G-FULL против G-PLAN при одинаковом входе и шаблоне |
| RQ-04 | Какова цена отказа от одного прохода? | G-PLAN/strict против ограниченного G-LOOP с учётом всех попыток |
| RQ-05 | Какая проверенная конфигурация дешевле при заданном качестве? | Лестница моделей и Pareto-сравнение cost, latency, quality |
| RQ-06 | Помогает ли сильному extractor визуальная обратная связь? | E-ONCE против E-LOOP при одинаковых источниках и лимите затрат |
| RQ-07 | Переносятся ли правила на новые статьи? | Отдельные unseen статьи с независимо подготовленными эталонами |
| RQ-08 | Как меняется экономия на сотнях статей? | Batch 100/200/300, очередь, расходы, ошибки и ZIP; сначала mock нагрузки |

Гипотеза H1: TemplatePackage + G-PLAN дешевле и надёжнее полной генерации размеченного текста за счёт меньшего ответа и сохранения payload. H2: подготовка шаблона с feedback улучшает повторное применение. H3: семантические inline-правила обобщаются лучше, чем перечень случайных жирных runs образца. Это гипотезы, а не заявленные результаты.

## Этапы

1. **Инструменты измерения.** Зафиксировать среду рендера, проверить повторный рендер одного и того же файла и управляемый renderer с oracle plan без LLM. Выявить визуальный шум и непокрываемые объекты.
2. **Шаблон вручную.** Исследователь/сильная OpenAI-модель составляет TemplatePackage, редактор проверяет. Знать образец здесь разрешено; хранить текст образца в runtime rules запрещено.
3. **Восстановление образца.** Из образца убрать оформление по протоколам I0/I1/I2. Для каждой фиксированной конфигурации выполнить 10 независимых применений. Ошибки источника, parser, planner и renderer классифицировать раздельно.
4. **Выбор application method.** Сначала проверить пригодность G-PLAN сильной моделью, затем сравнить G-FULL и G-LOOP в ограниченной матрице. Дешёвый G-RULES baseline нужен, чтобы не приписать модели работу детерминированных правил.
5. **Лестница моделей.** Если конфигурация проходит gate, проверить более дешёвые/быстрые кандидаты. Не предполагать монотонную зависимость качества от размера. Для каждой модели разрешена одинаковая заранее выделенная настройка на development split.
6. **Перенос.** Заморозить шаблон и prompts; применить кандидатов к unseen статьям. Для каждой новой статьи должен быть отдельный целевой DOCX, оформленный редактором по тому же шаблону. Пиксели исходной разнооформленной статьи не являются эталоном целевого оформления.
7. **Извлечение.** На лучшем известном application method сравнить методы создания шаблона. Это отделяет слабый extractor от слабого student. Затем проверить взаимодействия лучших комбинаций, не заявляя о полном факторном поиске.
8. **Пакет.** Проверить очередь, отмену, частичные ошибки, budget и ZIP на сотнях документов. Качество LLM и пропускная способность очереди измеряются отдельно.

## Что считаем одним проходом

Режим `strict_one_pass`: один запрос модели на целую статью, один полученный ответ, без repair, tool calls, скрытого chunking, второго классификатора, ручных правок и ответа из application cache. Парсинг, сборка и независимые проверки могут состоять из многих программных операций. Внутренние reasoning tokens модели учитываются в usage, но не считаются внешним agent loop.

Если документ не помещается по input/output limits, конфигурация получает `CONTEXT_OVERFLOW`, а не незаметный переход к chunks. Transport retry при неопределённом ответе отдельно отмечается; такой прогон не проходит строгий gate «один API attempt». Все попытки входят в стоимость. В production повтор допустим как другой явно обозначенный режим.

## Выбор минимальной конфигурации

«Самая маленькая» по параметрам применимо только к моделям с опубликованным размером. Основные критерии для API-моделей: стоимость принятого документа, p95 времени и pass rate. Отчёт показывает Pareto frontier и конкретный выбор при заданных бюджетах, а не выдуманный размер закрытой модели.

Амортизированная стоимость: `C(N) = C_template/N + C_application + C_validation + C_expected_retries + C_review`, отдельно показать машинные расходы и время редактора. Для failed attempts расходы сохраняются. Prompt caching провайдера, тарифная дата и batch discounts фиксируются; cached response не считается новым испытанием модели.

10/10 — эмпирический успех на данной ячейке эксперимента. Даже при независимых испытаниях нижняя граница двустороннего 95% Clopper–Pearson для 10/10 около 69%; повторы одной статьи ещё и не являются выборкой разных документов. Поэтому нельзя заявлять гарантированную 100% точность. Неуспех exact match не скрывается заменой его на высокий SSIM.

## Критерий завершения исследования

Есть хотя бы одна полностью измеренная цепочка, отчёт по всем 10 повторам (включая сбои), сравнение с baseline и результат на unseen документах. Если ни один кандидат не проходит строгий pixel gate, вывод — «подходящий кандидат не найден» с разбором причин и отдельной оценкой практического качества. Порог близкого визуального совпадения можно утвердить отдельно; он не переименовывается в 100% совпадение.

Открытые зависимости: разрешённый корпус, эталонные изображения/Word, доступные модели, тарифы и бюджет. Настоящие вызовы моделей и платные эксперименты в рамках текущего изменения документации не выполняются.
