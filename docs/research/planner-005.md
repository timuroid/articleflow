# Planner 005: модель выбирает варианты шаблона

Дата: 15 октября 2026 года. Реализован [компактный планировщик](../tech/compact-planner.md), который соединяет GPT-6.1 Sol с точным сборщиком 0.4. **Полное совпадение: 0/10 в замороженной серии.** Минимальная модель не выбрана; переход к более дешёвой модели не выполнялся.

[Все попытки CSV](planner-005-results.csv), [машиночитаемые метрики](planner-005-summary.json), [предыдущий oracle-контроль](renderer-004.md). Статья, template contents, prompt и ответы остаются приватными.

## Протокол и разделение результатов

Модель: `openai/gpt-6.1-sol`, выпуск 29 сентября 2026 года, повторно подтверждённый [официальным журналом](https://developers.openai.com/api/docs/changelog). Тариф маршрута: $2/1M входа, $10/1M выхода; cache read $0.10, cache write $2.50. Один запрос на всю статью, reasoning medium, max_tokens=24000, без temperature, repair и запасного провайдера. Oracle/golden не передаются модели. Сборщик получает полный compiled plan только из её ответа.

Модель выбирает paragraph/character variants, оформление таблиц, рисунков и секции. Текст сохраняется в content. Выделения адресуются точной цитатой и номером вхождения, затем компилируются в offsets. Это структурированный вход с непрозрачными формулами, **не строгий I1**.

Диагностика A: один запрос за $0.170321. JSON покрывал 178 блоков, но один character style не соответствовал выбранной роли. Валидатор остановил сборку: `PLAN_CHARACTER_STYLE`. Попытка сохранена, в десять прогонов B не включена.

В конфигурации B допустимые стили связаны с ролью через JSON Schema `anyOf`. Её prompt/schema/template/input/settings заморожены и совпадают во всех десяти запросах. Между первым запросом и продолжением обнаружилась нестабильность порядка JSON-ключей между Python-процессами. Preflight остановил запуск **до HTTP POST**; продолжение теперь сохраняет точную сериализацию первого запроса при проверке смыслового равенства входа. Это не замена ответа и не дополнительный model trial.

## Измерения серии B

Всего попыток: 10; дошли до сравнения DOCX/PDF: 9. Диапазоны ниже относятся к оценённым результатам; полный gate учитывает все десять попыток.

Десятый ответ содержал пересекающиеся цитатные выделения и завершился `QUOTE_OVERLAP` до сборки. Он не исправлялся и не заменялся повтором. Его качество DOCX не измерялось, стоимость включена в серию. Во всех девяти оценённых планах роли каждого из 178 блоков определены правильно.

Доля отличающихся пикселей: 10.3026–14.0284% при 144 DPI в прежней закреплённой среде LibreOffice. Равенство character style IDs — строгая диагностическая метрика, не процент визуально правильного текста: различающиеся свойства могут выглядеть одинаково. Точные значения inline flags и пикселей сохранены отдельно в CSV.

Текстовые блоки совпали в 9/10, OMML — 9/10, таблицы — 9/10, media bytes — 9/10. Ошибки защищённых верхних/нижних индексов дают content failure даже при сохранённых буквах и цифрах. Кандидат с такой ошибкой не принимается как готовая статья. Непринятые файлы остаются исследовательскими артефактами.

В первом результате разбор по флагам выявил 21 символ с неверным bold, 3 с неверным italic и 2 с неверным vertical; группы могут пересекаться. Общая точность inline-флагов — 99.9288%, однако даже две ошибки индексов нарушают критерий сохранности научного содержания.

В первом прогоне расхождения свойств абзацев затрагивали интервалы, отступы, границы, style references и формат знака абзаца; больше всего ошибок было среди spacer и bibliography. Правильная смысловая роль сама по себе не задаёт эти детали. Это продолжает наблюдение 0.4: сборщик точен при полном правильном плане, выбор этого плана ещё неточен.

## Контроль неоднозначности

Созданы два синтетических DOCX с одинаковыми текстами и одним каталогом двух вариантов выравнивания. Назначения выравнивания поменяны местами. **Model input полностью одинаков, а рендеры отличаются на 10 808 пикселей.** API не использовался; hashes и метрики записаны в summary, аналогичный контроль включён в тесты.

Это конструктивный пример того, что из текста и списка возможных свойств нельзя гарантированно восстановить любое исходное назначение. Он не доказывает невозможность восстановить именно данную статью при более подробных правилах. Следующий этап должен уточнять условия применения вариантов либо явно менять входной протокол, а не объяснять все ошибки размером модели.

## Бюджет и проверки

Диагностика A: $0.170321. Серия B: **$0.7981526**. Новые API расходы: **$0.9684736**. Накопленные расходы всего исследования: **$2.5089958**, неопределённый резерв: $0; предел этапа $5.

В 9/10 запросов B провайдер использовал кэш входных токенов; ответы генерировались заново. Это соответствует запрету application response cache. Повторение одной статьи дешевле потока разных статей: эти расходы нельзя без проверки экстраполировать на batch из 100 документов.

Офлайн: 36 unittest и 10 Gherkin-сценариев без API. Проверены текстовая неизменность, точные Unicode-цитаты и повторения, отсутствие oracle в planner input, отказ при ошибке, заморозка запроса и бюджет с учётом cache-write тарифа. Точность в Microsoft Word и независимый transfer пока не измерены.

## Следующий измеримый этап

1. Превратить наблюдаемые варианты в правила с условиями: контекст раздела, тип подписи, соседство таблицы, начало/конец списка. Не добавлять lookup по тексту, block ID или номеру абзаца образца.
2. Отдельно сохранить научно значимую исходную разметку индексов/формул в I2/I3 и измерять этот протокол отдельно от plain-text реконструкции.
3. Проверить семантический compiler и правила на синтетических контрпримерах и независимой статье, затем повторить сильный baseline. Уменьшать модель только после прохождения полного gate.

Веб-очередь, ZIP и универсальный extractor по-прежнему не реализованы; исследовательский CLI не объявляется готовым продуктом.
