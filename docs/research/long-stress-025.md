# Длинные синтетические эталоны: серия 025

## Вопрос и протокол

Проверяем, теряет ли extractor оформление длинного DOCX и какие наблюдаемые
различия компилятор способен превратить в переносимые правила. Это компонентный
эксперимент **с известными ролями**, не измерение точности большой или малой LLM.
Внешних API-вызовов нет. Известные роли доступны компилятору как отдельный
контролируемый вход; oracle-план используется только для проверки сборщика.

12 самостоятельно сгенерированных документов, 6 семейств, 2540 абзацев с учётом
ячеек таблиц. В каждом семействе seed=1 — эталон, seed=17 — новый документ:
меняются числа, длина текста и количество абзацев. Test не участвует в fit.
Это две реализации одного генератора, а не независимый реальный корпус.
Первые четыре семейства содержат более 200 абзацев на документ; двухколоночное
и отрицательное семейство — 151/159. Таблицы имеют повторяющуюся строку заголовка,
вложенную таблицу, длинный блок из 34 строк; разделы повторяются, библиография
имеет висячий отступ, после таблицы требуется иной интервал.

1. Извлечь полный каталог свойств и структуру.
2. Собрать DOCX по evaluator-only oracle-плану; проверить четыре инварианта
   целостности и каждый пиксель всех страниц при 144 dpi.
3. По одному эталону построить переносимый пакет с известными ролями.
4. Снять оформление входных документов через neutralize, применить пакет
   к эталону и held-out. Semantic emphasis остаётся объявленным входом системы.
5. Для каждого поддержанного эталона увеличить заголовок с 16 до 24 pt:
   сравнение обязано обнаружить отрицательный контроль.

Шрифты Arial/Times New Roman установлены точно. Движок: LibreOfficeDev
26.8.0.0.alpha0, build 2c87e51eeaa2b413ff4ae097b2705eea1995d8e5.
Результаты относятся к этому движку; совпадение в Microsoft Word не проверено.

## Результаты

| Семейство | Страниц эталон / test | Конфликтов при fit | Перенос на test |
|---|---:|---:|---|
| Вложенные и длинные таблицы | 15 / 16 | 0 | Полное пиксельное совпадение |
| Жирный цветной термин, курсив, верхний/нижний индекс | 15 / 18 | 0 | Полное пиксельное совпадение |
| То же + Arial внутри обычного Times New Roman | 15 / 18 | 5 | needs_review, 171 неразрешённое назначение |
| То же + чередование отступов 709/720 twips | 15 / 18 | 6 | needs_review, 211 неразрешённых назначений |
| Две колонки, подписи и таблицы | 6 / 7 | 0 | Полное пиксельное совпадение |
| Текстовые колонтитулы | Не извлечены | Не применимо | CATALOGUE_STORY_UNSUPPORTED |

Полный каталог и oracle-сборщик: **10/10 поддержанных документов, 143/143
страницы совпали**, все четыре проверки целостности прошли. Два отклонённых
документа остаются в знаменателе покрытия: 10/12, а не «100% поддержки».
Все пять отрицательных контролей обнаружены.
Перенос на новые документы: **3/6** test-документов всей серии; **3/5** среди
поддержанных. Четыре needs_review включают два эталона и два test-документа.
Необработанные документы не считаются успешным восстановлением.

## Причины и выводы

Контролируемое сравнение typography и typography_marked отличается только
прямым назначением Arial двум обычным фрагментам каждого body-абзаца. При его
устранении конфликтов 0 вместо 5 и held-out совпадает. Следовательно, в этих
примерах узкое место — недостаточная выразительность inline-признаков:
обычный текст и переменная имеют одинаковые bold/italic/vertical-признаки.
Цвет жирного термина восстанавливается, поскольку он однозначно связан с bold.
Это не доказывает поддержку произвольного распределения цветов.

Отступы 709/720 twips специально чередуются без смыслового основания.
Одинаковый контекст роли не позволяет вывести корректное правило переноса.
Система сохраняет варианты и отказывается угадывать — согласно требованиям.
Нельзя устранять этот конфликт округлением или правилом по ID абзаца.

Следующий инженерный шаг — семантические роли внутри абзаца (например,
переменная/термин) с ограниченными диапазонами и проверкой покрытия; после
изменения нужны новые held-out примеры. Колонтитулы требуют отдельной поддержки
stories и ресурсов, а не изменения prompt. Эту серию нельзя выдавать за
проверку полного teacher-agent-loop: нужны реальные модельные запуски с
единым действующим журналом расходов. Результаты модели здесь не выдумываются.

## Воспроизведение

```bash
FONTCONFIG_FILE=/path/to/fonts.conf .venv/bin/python scripts/benchmark_long025.py --output artifacts/long025-new
.venv/bin/python -m unittest discover -s tests -p test_long025.py -q
```

Генератор сохраняет эталоны, neutral DOCX, каталоги, планы, конфликты, PDF,
отрицательные контроли и итоговый JSON в указанной папке. ZIP timestamps не
фиксированы; SHA каждого созданного файла отражён в manifest. В публичном Git
хранятся генератор и результаты: [данные](../../datasets/long-v025/map.md).
