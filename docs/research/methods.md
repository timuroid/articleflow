# Сравниваемые методы

## Извлечение шаблона

| Код | Метод | Вход и результат | Ограничение |
| --- | --- | --- | --- |
| E-MANUAL | Шаблон составляет исследователь с сильной моделью | OOXML measurements + просмотр образца → проверенный TemplatePackage | Первый baseline, учитывать ручное время |
| E-RULES | Только программное извлечение | OOXML effective properties и частоты → наблюдения, role heuristics | Семантику терминов часто определить нельзя |
| E-ONCE | Один вызов сильной модели | Наблюдения и разрешённые изображения страниц → draft package | Один ответ может пропустить исключения |
| E-LOOP | Ограниченный агентный контур | inspect → propose → compile → render → diff → revise | Начальный лимит 5 model calls на шаблон + денежный предел; все вызовы учтены |
| E-EXTERNAL-JSON | Внешний Codex/редактор готовит строгую семантическую разметку | Тот же OOXML-извлекатель + `roles/groups/inline_roles/inline/questions` → draft package | Ассистированная разметка; ни ноль конфликтов на train, ни проза не удостоверяют перенос |

Все методы создают один и тот же контракт; validator и renderer одинаковы. Агент получает безопасные инструменты чтения OOXML-наблюдений, выбора фрагментов, проверки схемы и запуска renderer. Он не исполняет произвольный код из статьи и не выдаёт себе разрешения. Порядок инструментов и результаты фиксируются. Сильная актуальная OpenAI-модель — предпочтительный кандидат для E-MANUAL/E-LOOP, конкретный model ID выбирается при запуске по реально доступным возможностям.

E-LOOP вправе смотреть target specimen при подготовке шаблона. Чтобы отличить обобщение от запоминания, audit проверяет отсутствие исходного текста, абсолютных block IDs/offsets и готовых страниц в runtime package, а также проводится тест на unseen статьях. Feedback test split не используется для правки замороженного шаблона.

Для E-EXTERNAL-JSON реализован [offline-импорт 037](../tech/external-semantic-import-037.md).
Внешний аналитический текст может подсказать различающие признаки и вопросы,
но сам по себе не задаёт исполняемый полный план: нужны точные метки **всех**
абзацев и проверенные цитаты/координаты inline-диапазонов. Компилятор берёт
OOXML-свойства из эталонов и сохраняет неоднозначности. Даже валидный импорт
без train-конфликтов остаётся `draft_compiled`, пока не пройдены независимые
испорченные входы и held-out. В протоколе фиксируются внешний автор/модель,
затраченные вызовы и время, контроль редактора и происхождение разметки;
`model_calls=0` в отчёте локального импортёра **не** означает отсутствие
затрат на её создание. Ассистированный результат нельзя включать в долю
полностью автономных шаблонов.

## Представление шаблона

| Код | Представление | Зачем сравнивать |
| --- | --- | --- |
| T-PROSE | Инструкция обычным текстом | Дешёвый baseline подготовки, возможны неоднозначности и лишние токены |
| T-JSON | Строгие rules для блоков, spans и объектов | Однозначные значения, validation, компактная компиляция |
| T-BUNDLE | T-JSON + renderer profile + сгенерированные style parts + manifest | Практическое хранение с воспроизводимостью |
| T-DOCX | Очищенный каркас DOCX со стилями/slots и правилами | Проверка необходимости Word-носителя; риск переноса случайных локальных настроек |

T-BUNDLE — проектная рекомендация, не доказанный победитель. Canonical rules хранятся один раз; prose prompt и DOCX/style parts являются детерминированно скомпилированными производными с hashes. Два независимо редактируемых источника одних правил запрещены. Проза для baseline выводится из того же утверждённого набора правил, чтобы не сравнивать разный объём информации.

## Применение шаблона

| Код | Что возвращает модель | Вызовы | Главный риск |
| --- | --- | --- | --- |
| G-RULES | Модели нет, только детерминированное mapping | 0 | Недостаточно семантики; baseline |
| G-FULL | Весь текст с блоками, spans, стилями и asset refs в JSON | 1 | Потеря символов, стоимость длинного ответа, truncation |
| G-PLAN | Ссылки на исходные блоки/диапазоны + роли и object bindings | 1 | Ошибки span boundaries и выбора правил |
| G-LOOP | G-PLAN с обратной связью schema/layout validator | ≤3 model calls на статью | Задержка, стоимость, потеря one-pass свойства |

Все варианты собирают DOCX кодом; прямое создание model-generated ZIP/base64 не требуется. G-FULL — полноценная проверка первоначальной идеи «расписать каждый текст и его свойства». Payload сравнивается с исходником, и изменённый научный текст блокирует результат. G-PLAN уменьшает ответ: один `role_id` заменяет повтор шрифта, интервала и отступов у каждого абзаца.

G-LOOP при применении новой статьи не получает её эталонный целевой DOCX или golden pixels. Ему доступны только исходный разрешённый контент, TemplatePackage и проверки правил/самого результата. Feedback от golden используется evaluator после завершения, иначе измеряется агент с недоступным в production ответом.

## Контролируемый дизайн

Сначала фиксируем E-MANUAL + T-BUNDLE + I1 и сравниваем G-RULES/G-FULL/G-PLAN/G-LOOP на сильном baseline. Затем у подходящих application methods понижаем стоимость модели. Потом меняем extractor и input protocols. Сравнение нескольких факторов одновременно допускается только как отдельная подписанная конфигурация, не как доказательство влияния одного фактора.

На одинаковой ячейке фиксируются template hash, input hash, output schema, provider/model revision, renderer, token budget, prompt, reasoning settings, temperature и seed если доступны. Порядок прогонов перемешивается или балансируется, чтобы загрузка провайдера и прогрев cache не совпадали с одной моделью. Одинаковый seed не доказывает независимость повторов.

Отдельно вести `patch_source` и `rebuild_neutral`. Первый сохраняет исходные OOXML objects и полезен в реальном сервисе. Второй восстанавливает документ из данных без исходного оформления и нужен для честного round-trip теста. Метод, оставляющий оформление образца в документе, не считается успешным восстановлением из plain text.

## Дополнительный профиль 0.7: исходный DOCX

[Source-aware I3](../tech/source-aware.md) переносит на модель только классификацию ролей. Compiler видит исходные свойства обрабатываемой статьи, сохраняет допустимые варианты и исправляет однозначно сопоставимую типографику. Совпадение на уже оформленном образце проверяет идемпотентность и классификацию; его нельзя считать восстановлением удалённых visual properties. Сравнение более дешёвых моделей внутри этого профиля не определяет минимальную модель для I1/I2.

[Source marks](../tech/semantic-marks.md) — отдельная абляция: source bold/italic/vertical присутствуют во входе, остальные свойства выбираются прежним планировщиком. Влияние этого дополнительного входа измеряется отдельно от I3.
